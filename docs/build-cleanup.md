# 빌드 산출물 관리

## 대상 및 실행

이 저장소는 Go 1.21 모듈과 Fyne 2.4.4를 사용하는 **데스크톱 게임**이다. 기존에는 README의 직접 `go run .`, `go test ./...`만 있었고 빌드 스크립트·CI·출시 설정은 없었다. 관리 실행기는 Python 3.9+와 POSIX 잠금/프로세스 그룹을 사용하는 macOS/Linux 개발 도구다. Windows 네이티브 실행기, 모바일·웹·콘솔, 서명된 설치본은 이번 범위에 포함하지 않는다. Go 버전이나 게임의 출시 설정을 변경하지 않는다.

```sh
make test-cleanup # 작은 가짜 도구로 정리/복구 검증; 실제 게임 반복 빌드 없음
make test         # 기존 게임/UI 테스트
make build        # 현재 플랫폼 개발 실행 파일
make package      # 개발 실행 파일 + LICENSE + README의 tar.gz; 실행 파일 중복 제거
make run          # 관리된 임시 디렉토리에서 go run .
make clean        # 유휴 잔여 작업 회수 + 보관 개수 적용; 전체 삭제 아님
```

`python3 -B scripts/build.py <명령>`도 같다. `make package`는 개발 확인용 압축본이며 Fyne 앱 번들·설치 프로그램·서명된 출시 패키지가 아니다. 폰트는 기존 `go:embed`에 의해 실행 파일 안에 포함된다. 생성 위치는 출력 메시지와 `.build/current.json`에서 확인한다. 오래 실행할 디버깅 세대는 아래 예외 절차를 따른다.

## 소유와 복구

- `.build/owner.json`은 도구 버전과 프로젝트 절대 경로를 기록한다. 표식이 없거나 다른 위치에서 복제된 `.build`는 자동 삭제하지 않는다.
- `.build/lock`의 OS 파일 잠금을 전체 작업 동안 유지한다. 다른 관리 작업은 경고와 실패 코드로 종료한다. 한 저장소의 빌드는 직렬화하여 게시/보관 경쟁을 없앤다. 여러 빌드를 동시에 해야 한다면 별도 체크아웃을 사용한다.
- 각 `.build/work/<무작위 ID>/`에 임시 파일과 진행 로그를 둔다. `GOTMPDIR`, `TMPDIR`, `TMP`, `TEMP`를 이 작업의 `tmp/`로 설정한다. 원본 작업 사본이나 에셋을 복제하지 않는다.
- 자식에게 잠금을 상속하고, 프로세스 그룹 ID를 디스크에 기록한 뒤 게이트를 열어 컴파일을 시작한다. 부모만 SIGKILL된 경우에도 살아 있는 자식의 잠금 때문에 회수하지 않는다.
- SIGINT/SIGTERM/SIGHUP 시 자식 그룹에 TERM을 보내고 최대 3초 뒤 KILL로 종료를 마무리한다. 그룹이 남아 있으면 경고하고 보존한다. 다음 실행(또는 CI의 `always()` 정리)이 소유 표식·잠금·그룹 종료를 확인해 잔여물을 회수한다. PID 재사용/확인 불가·손상된 표식은 보수적으로 보존한다.
- 하위 디렉토리 이름만으로 삭제하지 않는다. 관리 영역 바로 아래의 작업 ID, 소유자, 종류가 일치해야 한다. 루트/분류 디렉토리 심볼릭 링크는 거부하고, 재귀 삭제는 확인된 소유 디렉토리에 한정한다. 초기 표식 작성 중 전원이 끊겨 표식 없는 디렉토리가 남는 경우에도 자동 추정 삭제하지 않는다.
- 빌드 도구는 자식 작업을 데몬화하거나 작업 수명 밖으로 분리하지 않아야 한다. 정리 실패는 `WARNING`과 남은 경로를 출력하고 성공 종료 코드로 숨기지 않는다. 강제 종료·전원 차단 자체를 처리하는 종료 훅은 없으며 다음 실행에서 복구한다.

## 게시와 보관

| 종류 | 위치/정책 |
| --- | --- |
| 작업 임시·중간 파일 | `.build/work/`; 종료/다음 실행에서 회수 |
| 개발 성공 실행 파일 또는 압축본 | `.build/dev/`; 현재 정상 참조를 포함해 완료 순서 최근 2개 |
| 원문 빌드/테스트/실행 로그 | `.build/logs/`; 작업당 파일 1개, 마지막 1MiB, 최근 10개 작업 |
| 검증 결과/정리 감사 기록 | `docs/storage-audit*`; 버전 관리, 자동 삭제 없음 |
| 출시본·패치 기준·롤백·심볼/매핑 | 자동 관리 영역 밖, 자동 삭제 없음; 배포 정책 확인 후 별도 관리 |
| Go 모듈/컴파일 공유 캐시 | 기존 `GOMODCACHE`/`GOCACHE` 유지; 빌드마다 삭제하지 않음 |
| 원본/설정/키/사용자 저장 데이터 | 정리 범위 밖 |

개발 실행 파일의 Go 빌드 정보를 읽어 확인하고, 압축본은 내부 실행 파일의 SHA-256까지 비교한다. 임시 세대에서 검증을 끝내고 파일을 동기화한 후 같은 파일시스템에서 완성된 세대를 이동한다. `current.json`을 원자적으로 교체한 뒤 오래된 개발 세대를 정리한다. 빌드/패키징/게시 실패는 이전 정상 참조를 바꾸지 않는다. 게시 직후 전원이 끊겨도 다음 정리에서 기존 현재 참조를 우선 보존한다. 개발 실행 파일은 심볼을 제거하지 않지만 **출시 크래시 분석용 심볼 보관소로 사용하면 안 된다**.

CI는 `.github/workflows/build.yml`에서 같은 실행기로 테스트·패키징하고 `always()`로 복구한다. 임시 macOS 호스팅 러너의 개발 패키지는 업로드하지 않아 실행별 패키지가 원격에 누적되지 않는다. 로그만 7일간 업로드한다. 원격 CI 로그는 실행 간 로컬 디렉토리가 이어지지 않으므로 최근 10회 대신 **7일 TTL**을 사용한다(각 실행 업로드는 10개·1MiB 제한 유지). GitHub 자체 콘솔/실행 기록은 서비스의 저장소 정책을 따른다. 출시 자료와 원격 캐시 삭제 API는 호출하지 않는다. 실제 원격 CI 실행은 저장소에 워크플로가 반영된 후 확인해야 한다.

Go의 임시/공유 캐시 구분은 [Go 환경 변수 문서](https://go.dev/cmd/go/#hdr-Environment_variables)를 따른다. 향후 네이티브 배포 패키징은 [Fyne 데스크톱 패키징](https://docs.fyne.io/started/packaging/)에 맞는 별도 검증/출시 보존 정책을 정의하고 같은 관리 수명 주기에 연결한다.
